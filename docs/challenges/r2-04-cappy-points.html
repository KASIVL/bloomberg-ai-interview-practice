Cappy Points

TICKET #04
OPENBUGPYTHON

Ticket: Cappy Points leaderboard can’t be trusted

Problem

Members earn Cappy Points by scanning the QR code at club events. Some members noticed their points go up every time they scan the same event’s code. Officers also report that the leaderboard on the lobby screen stops changing after the first time it loads, until an officer makes a manual adjustment. Investigate the check-in flow across the routes, check-in service, attendance log, points ledger, and leaderboard.

Acceptance criteria

  • Each student earns points for a given event at most once, no matter how many times they scan.
  • Different students at the same event, and the same student at different events, all earn points.
  • Event points are 10 for CIC, 15 for ICPC, and 5 for socials; unknown events and incomplete requests are rejected.
  • The leaderboard reflects every check-in and officer adjustment, ranked by points with ties broken alphabetically by student ID.
  • Repeating a check-in returns the student’s current balance without changing any state.
  • Everything uses the included in-memory classes; no external service is needed.

Investigation

Scan the same event twice and watch both the response and the ledger balance. Then follow one check-in through every class it touches and note which shared state each step reads or writes. Check whether the starter tests assert the balance or only the status code. Make a focused fix and add regression tests for the state transitions you verify.

Follow-up: system design

Once your tests pass, talk this through with your table: check-in now runs on three servers behind a load balancer, and 5,000 students scan the QR code in the first five minutes of a big event. Each server keeps its own attendance log, ledger, and leaderboard cache. What goes wrong, and what would you change?
